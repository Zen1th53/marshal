## Design decisions worth recording

1. **`app.Open` was not made lenient.** It is the execution runtime and its
   strictness is correct. Assessment runs *before* and *independently of* it,
   so a runtime that cannot open becomes a described condition rather than a
   terminated process. Execution stays gated exactly where it was.
2. **Only one core-fatal condition exists** (an unwritable state directory),
   and the set is explicitly enumerated rather than derived from whichever
   check failed, so it cannot grow by accident.
3. **The protected surfaces cannot be removed by any check.** A test supplies a
   hostile check that declares Doctor, Setup and Help as its own capabilities
   and asserts they survive.
4. **`LIMITED` permits execution.** Two aggregation bugs were found by running
   the real binary against a fresh project: an absent optional capability was
   escalating to NEEDS_ATTENTION, and LIMITED was blocking work. Both are
   fixed with regression tests. Egress enforcement is unavailable on most
   developer machines, and treating that as grounds to withhold the workspace
   made the common case look broken.

## Setup / Doctor status

| Surface | Assesses | Explains | Mutates |
|---|---|---|---|
| Setup | yes | — | **never** (no write path exists) |
| Doctor | yes | yes | only with consent |
| Repair | — | — | yes, then re-tests |

`Fixed` requires the failing check to be re-run and pass. A repair whose
command exits zero but leaves the problem in place reports
`ATTEMPTED_NOT_FIXED`. A repair whose result cannot be confirmed reports
UNKNOWN. Consent is a field the caller must set and is bound to the diagnosed
condition, so it cannot transfer to a different problem.

The self-repair set contains exactly one condition. Twelve others — installing
Git, creating a repository, provisioning a sandbox, writing policy, granting
entitlement, repairing corrupt state — are covered by a test asserting MARSHAL
declines to act on the user's behalf.

## Process 00 integration

Process 01 is subordinate throughout. Startup observes, classifies, explains
and recommends. It does not mark anything Ready it did not verify, authorize a
repair, enable ULTRA, weaken sandbox or network policy, or declare provider
qualification — all of which remain constitutional decisions in
`internal/constitution`. Sandbox and network facts are read from the same
`app` helpers the runtime uses when deciding whether work may execute, so the
control center cannot report Ready for something the runtime would refuse.

## Limitations (stated plainly)

1. **No MARSHAL-mediated provider E2E.** No endpoint-enforcing egress backend
   exists in this environment. NOT_RUN is the only honest result; isolation was
   not weakened to obtain a pass.
2. **Provider readiness is modelled but not fully probed.** The four-fact
   distinction is implemented and documented; per-provider detection still
   delegates to the existing Doctor probes rather than reporting all four
   facts separately per provider.
3. **Web and MCP/A2A do not yet surface the startup assessment.** They retain
   their existing behavior, unchanged rather than weakened.
4. **No readiness cache.** Assessment is fast enough that caching would add
   staleness risk without a measured benefit. Recorded as NOT_RUN rather than
   claimed.
5. **Telemetry and performance budgets were not measured.**
6. **The working tree still carries the unrelated uncommitted TUI work**
   present at baseline, verified green and left untouched. The regenerated
   manifest reflects that tree.
