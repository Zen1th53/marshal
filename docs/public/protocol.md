# Planning with the Marshal

The Marshal introduces itself, asks your language, and offers to continue earlier
work. It then reads the project's current state, clarifies your goal, agrees the
working mode and control level with you, and writes the plan pack.

Whenever a protocol decision changes MARSHAL state, MARSHAL opens its English
**Permission request** popup. The Marshal says: **“MARSHAL will show a popup;
press A to apply.”** The working-mode question includes its recommended setting
proposal immediately, so you can decide in the popup.

Read the exact setting, path, memory candidate or plan action and its scope.
Press uppercase **A** to apply the displayed change. Any other key, closing the
popup, or 120 seconds without an answer declines (30 seconds for credential
requests). A chat reply such as “done” does not approve a change. You do not
need to type `/marshal` commands in the provider chat or a shell.

This applies to acceptance mode, execution rights, control level, rework limit,
concurrency and budget settings; read access to earlier work; individual memory
candidates; and plan approval. Task acceptance, returns, amendments, continuation
and final delivery can also be proposed for operator popup decisions. Settings
follow the existing settings command: they apply to the next Marshal run.

Read the plan pack before allowing plan approval. Approval starts the existing
worker workflow. MARSHAL binds run actions to the plan version and state shown
in the popup and refuses an outdated proposal. MARSHAL records each popup
allow or decline as operator evidence and delivers the outcome to the Marshal's
inbox. Earlier-work reads remain limited to the granted project history, and
memory candidates retain their provenance.

The native provider may still have its own filesystem tools and permissions.
A MARSHAL read grant governs MARSHAL's continuation reader; it does not confine
the provider CLI.

The model only proposes. MARSHAL accepts strictly parsed, allow-listed proposal
lines from visible assistant output in the bound Marshal conversation. Unknown
or malformed proposals are ignored and logged. Repeated identical proposals in
that conversation do not reopen or stack popups, including after a decline.
Manual commands remain available in MARSHAL's own composer.
